## CHECK 3c — Gateway and private-registry operators

**The one question:** what do you use *today* to decide whether an MCP server may be
admitted?

Check 3b already established from primary documentation that Azure API Center's
registration flow captures only metadata and describes no admission criteria. The open
question is what operators do in the gap that leaves.

### Targets

| Organization | Team / role | Why they are relevant | Specific question |
|---|---|---|---|
| Microsoft — Azure API Center | PM for API Center / MCP registry | Ships the largest documented organizational MCP registry. Registration captures metadata only. | Do customers ask what should gate registration, and what do you tell them? |
| Microsoft — Copilot Studio MCP certification | Certification PM (`ms.author` on the certification page) | Owns the one process that explicitly invites evaluation evidence. | What does submitted evaluation evidence look like in practice, and has any been third-party produced? |
| Cloudflare | MCP portals / Cloudflare One | Operates an admission surface for organizational MCP access. | What does an admin see when deciding to add a server to a portal? |
| AWS | MCP Gateway / Bedrock AgentCore | Registry plus gateway in one product. | Is there an approval step, and what informs it? |
| GitHub | Copilot policy / MCP registry | Today the control is a binary enable/disable. | Are per-server controls planned, and what would inform them? |
| Any enterprise platform team running an internal MCP allowlist | Platform / AppSec lead | The actual ICP. Reachable through MCP and agent-infrastructure communities. | The message below, unchanged. |

### Message

> Subject: What do you use to decide an MCP server is OK to add?
>
> Hello — you run [the registry / the gateway / the allowlist], so you are making a
> decision I am trying to understand properly.
>
> When a new MCP server is proposed for your organization, what do you actually look at
> before allowing it? I am after the real answer, including "the package name and who sent
> me the link" — that is the answer I expect most often and it is the useful one.
>
> Three specific things:
>
> 1. Is there a written criterion, or is it judgement?
> 2. Does anyone run the server and look at what its tools do, or is the decision made from
>    its description and schemas?
> 3. After you approve it, does anything tell you when the server changes?
>
> Context so you know why I am asking: I build execution-based verification for MCP servers.
> It runs each tool in an isolated container and records what the tool actually did against
> what the server declared about it — for example a tool annotated `readOnlyHint: true` that
> writes. I am trying to find out whether that is an input anyone doing your job wants, or
> whether it solves a problem you do not have. Either answer is worth the email to me.
>
> Thank you.

### Why the third question matters most

Anthropic's own connector verification page tells users to *"Monitor for unexpected changes
in tool behavior"* and ships nothing that does it (quoted in
[GATE0_EVIDENCE.md](GATE0_EVIDENCE.md)). If operators answer "nothing tells us", that is
the F4 signal. If they answer "we do not care", the drift thesis is weaker than the PRD
assumes and Gate 2 should be re-scoped before anything is built for it.
